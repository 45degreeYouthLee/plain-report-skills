# 技术与架构：怎样做到不是黑盒

负责人不读代码，但要能回答五个问题。架构区的每一部分对应其中一个：

| 负责人要能回答 | 页面上的部分 | 数据 |
|---|---|---|
| 系统由哪几块组成，怎样配合？ | 一句话全貌 + 分层图 | `overview`、`layers` |
| 每块做到哪、有没有证据？ | 各模块表（状态、验证程度、证据日期、代码位置） | `modules[].status / proof / paths` |
| 一件事在系统里怎样走完？出问题怎么办？ | 主流程（1–3 条） | `flows` |
| 哪些约束不能破，现在守住了吗？ | 架构规则 | `rules` |
| 为什么这样设计，放弃了什么？有什么技术风险？ | 架构决定、技术选型、技术风险 | `decisions`、`stack`、`risks` |

再加一项自动检查：**黑盒检查**。它对照仓库目录，找出架构图上没有的代码和图上有但仓库里没有的模块。

## 从哪里取材

按顺序读，越靠前越可信：

1. **代码目录结构：** 顶层和第二层目录各是什么。
2. **项目自己的架构、设计、接口文档：** 名字里常有 ARCHITECTURE、DESIGN、PROTOCOL、API、ADR。
3. **构建与依赖文件：** `package.json`、`*.csproj`、`pyproject.toml`、`go.mod` 等，用来写技术选型。
4. **测试与验收记录：** 用来写各模块的验证程度和证据日期。
5. **任务汇报：** 只用来补最近的变化和问题。

文档和代码对不上时，以代码为准，并把不一致写成一条 `forYou`（知晓）。

## 分层怎么分

- **按"负责人能理解的职责"分层，** 不按代码语言或框架分。典型分层：接入层（谁来调用）、核心层（主要逻辑）、数据或内核层（依赖的底座）、界面层（人看到的）、验证工具（证明能用的）。
- **一层 1–6 个模块。** 超过就拆层或合并模块。模块数控制在 20 个以内；更细的放在模块的 `paths` 里。
- **外部依赖也要画出来**（内核、云服务、第三方接口）。标 `"external": true`，不要求代码位置。
- **每个代码目录都要归到某个模块。** 黑盒检查查出没归属的文件，先读文件开头弄清用途再归类；弄不清就留着，让它出现在页面上。

## 验证程度

| 词 | 用在什么时候 |
|---|---|
| 已验证 | 有专门的测试或实测覆盖，结果通过，写出数字和日期 |
| 部分验证 | 有测试，但范围受限、有未过项，或关键场景没测 |
| 未验证 | 做了，但没有任何测试证据；或测试失败 |
| 未知 | 找不到相关记录 |

不因为"代码写完了"就写已验证。证据超过 14 天（可用 `staleDays` 调整）页面会标"证据过期"。

## 架构规则从哪来

- **负责人定的原则和边界**（产品裁决、安全隐私边界、资源上限）。写 `"by": "用户"`。
- **执行方的设计约束**（"每份资源只有一个拥有者""日志不记录输入内容"）。写 `"by": "Codex"`。
- **状态：** 有测试或实测证明遵守写"遵守"；发现违反写"有偏离"，同时加一条 `forYou`；没核对写"未核对"。

## 什么时候更新

- **新增或删除模块、改变模块边界、换技术选型、改通信方式：** 更新架构区，并加一个 `"arch": true` 的历史节点。
- **模块有了新的测试结果：** 只改该模块的 `proof`。
- **每次更新都重跑黑盒检查。**
