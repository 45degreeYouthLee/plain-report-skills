# 项目追踪

**目标：** 让不读代码的负责人能把控整个项目：知道系统由什么组成、各块验证到哪、技术上守住了哪些约束、项目沿什么路线走到这里、现在要他处理什么。

**和任务汇报的分工：**

| | 任务汇报（report-explain） | 项目追踪（本技能） |
|---|---|---|
| 回答 | 这一轮做了什么、变了什么、下一步 | 项目整体在哪、架构是否可控、路线怎么走过来的 |
| 节奏 | 每轮汇报 | 架构变化、阶段变化、关键决定时更新；平时只改受影响的部分 |
| 关联 | 事项可以挂到追踪页的模块和工作线 | 工作线链接到它的任务汇报页 |

## 固定的和开放的

**固定（每个项目都有，不能省）：**
1. **项目目标与不做什么。**
2. **技术与架构。** 不读代码的人唯一能把控技术的地方，不能是黑盒。内容见 `references/architecture.md`。
3. **历史节点。** 按日期记录里程碑、关键决定、方向调整、问题、阶段验收、架构变化。
4. **需要你处理。** 待决定、待批准、待验收、需要你动手、需要你知道的事。

**开放（按项目和负责人定，不预设）：**
- **工作线：** 项目由哪几条线一起推进，每条线谁主导（用户 / Codex / 共同）、产出什么、按什么节奏。Agent 可以提议，但不删除、不评判负责人加的线；负责人主导的线（例如视觉）Agent 只记录规范、核对偏离、列出待确认，不催进度。
- **产物类型：** 不预设"产品文档 → 原型 → 视觉 → 代码"。产物是什么由各条线自己定。
- **阶段：** 可选。执行方有内部编号（如 A-13）时，必须翻译成"是什么、怎样算过关"；查不到说明的编号标"未说明"，列入需要你处理。

## 流程

### 第一次建立

1. **读项目，不读汇报。** 读 README、架构与设计文档、接口文档、测试状态、计划文档、目录结构。任务汇报只用来补历史节点。
2. **写 `tracking.json`**，格式见 `references/tracking-data.md`，可照 `examples/minimal/` 写。先写技术与架构，再写工作线。查不到的写"未知"，推断的写明是推断，不编。
3. **对照仓库做黑盒检查：** `node <本 skill 目录>/scripts/scan-repo.mjs <仓库根目录> <tracking.json>`。列出"图上没有"的代码和"仓库里没有"的模块路径。先读这些文件弄清用途，再归到模块；弄不清的保留在结果里，不硬塞。
4. **构建：** `node <本 skill 目录>/scripts/build-tracking.mjs <tracking.json> _reports/<项目>-tracking.html`。数据错误会停下；提示（证据过期、规则未核对、编号未说明、负责人的线还空着）逐条处理：能补就补，补不了的放进 `forYou`。
5. **真实浏览器看一眼：** 桌面和手机宽度，点一下历史节点筛选。

### 之后更新

- **触发：** 架构变化（新模块、边界或依赖变了）、阶段开始或验收、负责人作出决定、方向调整、新增或停掉工作线。普通的任务轮次不触发，只在对应任务汇报里写。
- **只改受影响的部分**，同时在 `history` 加一个节点，写清影响；架构变化的节点标 `"arch": true`。
- **每次更新都重跑 scan-repo.mjs。** 架构图跟不上代码，就是黑盒在形成。
- **模块的证据有日期。** 超过 `staleDays`（默认 14 天）构建会提示，页面标"证据过期"。

## 写法

遵循 `report-explain/references/writing.md`，另外：

- **模块的"它做什么"写作用，不写类名：** "AI 掉线后空间按租约自动回收"，不写"Sessions.Registry 管理 lease"。
- **"建成"和"验证"分开：** 每个模块分别写状态（建到哪）和验证程度（已验证 / 部分验证 / 未验证 / 未知）加证据。没有证据就是"未知"，不因为代码存在就写"已验证"。
- **架构规则写成"不能破的约束"，** 并写为什么、谁定的、现在是否遵守。没核对过就写"未核对"。
- **决定写清谁定的**（用户 / Codex / 共同）。负责人授权执行方拍板的，也作为一个历史节点记下来。

## 交付时在聊天里写什么

- 页面路径和一句整体判断。
- 黑盒检查结果（几个目录、几处没对上）。
- 构建提示里没处理的项及原因。
- 要核对：1–3 件负责人应该自己确认的事（通常是推断出来的状态、未说明的编号）。
