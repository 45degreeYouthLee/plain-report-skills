# 汇报与讲解规范（核心）

**目标：** 用户第一眼就能建立整体框架，再按需看细节。框架比细节重要。语言简单，内容不少。

**谁用：**
- **执行任务的 agent（主要是本机 Codex）：** 进度汇报、阻塞说明、请用户拍板都按本规范写。
- **云端 Claude：** 回答大方向、架构、技术对比时用。

本文件是核心规则，每次都读。细则在 `references/` 里，**用到哪部分才读哪个文件**：

| 要做的事 | 读 |
|---|---|
| 写任何中文段落（几乎每次） | `references/writing.md` |
| 写进度汇报、阻塞、事故、决策请求 | `references/reports.md` |
| 画图 | `references/figures.md` |
| 讲状态机、队列、请求路径、架构演进，且静态图讲不清 | `references/motion.md`（扩展项，不默认） |
| 出 HTML 页面 | `references/pages.md`，并调用 `report-page-style` 取样式和模板 |
| 想知道某条规则从哪来、为什么 | `references/sources.md` |

## 一、流程：每次走这五步

1. **判断内容类型和汇报类型。**
2. **选格式**（第二节）。
3. **先写文字底稿。** 所有事实都在底稿里；图和页面不加底稿里没有的事实。
4. **需要时再出图或页面。**
5. **写结尾，做自检**（第四、五节）。

## 二、选格式：选够用的最低一级

| 情况 | 格式 |
|---|---|
| 问答、单个事实、单个简单决定 | 聊天文字 |
| 有交叉关系、分支、对比，文字说不清 | 聊天文字加一张图或一张表 |
| 用户要反复看、要转给别人、超过一屏、或要在多个选项里拍板 | 单文件 HTML 页面 |

- **用户点名格式时，按用户的。** 内容混合时，按最难懂的部分选。拿不准时降一级，结尾一句话提议升级。
- **有页面时，聊天里只写结论和路径或链接。** 不把内容再写一遍。
- **页面存放：** 本机 agent 存 `_reports/<日期>-<主题>.html` 并给路径；能发布 Artifact 的环境发布并给链接。
- **动画是扩展项：** 只在第一节第 4 步确认静态图讲不清时加，见 `references/motion.md`。
- **不做：** 讲解视频；为展示而逐级重复同一内容。

## 三、六条核心规则

1. **先全景，后细节。** 开头一屏放下全部对象和它们的关系。
2. **重点能扫读。** 第一句写结论；每行以加粗关键词开头；一组 3–5 条。
3. **内容不删。** 数字、条件、"通常""可能"都保留；标明**实测 / 推断 / 未知**。
4. **图必须带来新信息。** 文字一句能说清的不画。
5. **交互只高亮和筛选，不隐藏。** 默认把全部信息摊开。
6. **对比才用表格，各做各的就用卡片。** 布局跟着内容量走，不留大片空白。

## 四、结尾（每次都要）

- **需要你决定：** 没有就不写。有就往细了讲：问题本身；每个选项的做法、牵连、成本、风险；推荐和粗略把握（标明是估计）；**结论在什么条件下会翻转**；一句话告诉用户回什么。格式见 `references/reports.md`。
- **要核对：** 1–3 件用户应该自己验证的事：关键数字、前提假设、和来源不一致的地方、没实际跑过的检查。格式越好看，用户越容易相信里面的错误。

## 五、交付前自检

- [ ] 第一句是结论吗？第一屏能看到全景吗？
- [ ] 只看加粗关键词，能知道每行讲什么吗？
- [ ] 有没有删掉事实、数字、条件或限定词？有没有残留填充语？
- [ ] 每张图都带来了文字给不了的信息吗？加动画的地方，静态图真的讲不清吗？
- [ ] 有没有用交互把信息藏起来？手机上有没有左右滚动条？
- [ ] 阻塞写清了四件事吗？决策写清了成本、风险、把握和翻转条件吗？
- [ ] 页面有更新时间吗？引用的日志、配置里有没有密钥（见 `references/pages.md`）？
- [ ] 结尾有"要核对"吗？
